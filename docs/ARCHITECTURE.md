# Steppy v1 architecture

Steppy is a step-count leaderboard for groups of friends. Each member's phone reads their daily
step totals from the phone's health store (Apple Health on iOS, Health Connect on Android) and
uploads them to a small API. The API ranks group members over today, this week, this month and
the last three months, and runs weekly and monthly challenges inside groups.

## What was kept from the scaffold and what was replaced

The repository started as an MVP scaffold: a NestJS + Prisma API with a synthetic "Developer"
provider and a provider-record data model, a pure domain package, a shared zod package, and an
Expo app with committed native projects and a one-shot Health Connect import.

v1 is a clean rebuild on the same stack:

| Piece | Decision | Why |
|---|---|---|
| pnpm monorepo, TypeScript | Kept | Fine as is. |
| NestJS 11 + Prisma 6 + Postgres | Kept the stack, rewrote the modules and schema | The stack suits a small REST + WebSocket API. The old data model (per-provider records, sync jobs, Google sign-in, achievements) did not match v1's groups, challenges and phone-hub source rule. |
| Socket.IO for live updates | Kept, redesigned | Now one `/realtime` namespace with per-group rooms. |
| `packages/health-domain` + `packages/shared` | Merged into `packages/core` | One package now holds the API contract (types and zod schemas) and the pure calendar/ranking rules. The API and the app both import it, so they cannot drift apart. |
| Expo SDK 57 / React Native 0.86 app | Kept the stack, rewrote the app | Screens, state and the Health Connect import were placeholders. |
| Committed `ios/` and `android/` projects | Replaced by prebuild | The native projects are generated by `expo prebuild` from `app.config.ts` and config plugins (HealthKit, Health Connect, background tasks), so entitlements and permissions live in one reviewed file instead of drifting in generated code. |
| Developer synthetic provider | Replaced | By a server demo mode (seeded friends that move live) and an on-device `DEMO` step source. |

## Data model

- `User`: email, password hash, display name, 8-character friend code, timezone, `stepSource`,
  `lastSyncedAt`.
- `Friendship`: one row per pair. Adding a friend by code is immediate and mutual.
- `Group` and `GroupMember`: owner and members, an invite code, and the group timezone used for
  leaderboard and challenge calendars.
- `DailySteps`: one row per user per local date, with the source and the uploader's timezone.
- `Challenge` and `ChallengeParticipant`: kind (`WEEKLY`/`MONTHLY`), start and end dates, and
  once finished the winners plus a snapshot of the final standings.

## Where the step numbers come from

**Source rule: the phone's health store is the source of truth.** The app reads daily totals
through the store's statistics APIs rather than summing raw samples:

- iOS: an `HKStatisticsCollectionQuery` with a cumulative sum over daily intervals anchored at
  local midnight. HealthKit merges iPhone and Apple Watch samples so the same steps are not
  counted twice.
- Android: Health Connect `aggregateGroupByPeriod` for `Steps` in one-day slices. Health Connect
  de-duplicates across writing apps using the user's data-source priority.

The server stores what the phone reports for each day and never adds sources together. If
someone switches phones, the latest upload for a day wins. WHOOP, Oura and the Google Health API
are deferred: people with those devices usually also sync them into Apple Health or Health Connect.

## Freshness

The honest promise shown in the app is: *live while you're in Steppy; otherwise friends update
roughly every 15 to 60 minutes; each day is final at 10:00 the next morning.*

| When | What happens |
|---|---|
| First connect | Ask for read permission, then upload the last 90 days (backfill). Android also asks for history access (to read older than 30 days) and background access. |
| App opens or returns to the foreground | Full refresh: re-read today and the last 2 days (plus any gap since the last sync) and upload. |
| While the app is open | Re-read every 60 seconds; upload when a value changed or 5 minutes have passed. Friends' uploads arrive over Socket.IO and refresh the open screens. Leaderboards also refetch every 60 seconds as a fallback. |
| Pull to refresh | Forced re-read and upload, then refetch. |
| Background, iOS | HealthKit background delivery (hourly) with an observer query registered at launch, plus a `BGTask` via `expo-background-task`. Best effort: iOS decides when to wake the app, and nothing can be read while the phone is locked. |
| Background, Android | `expo-background-task` (WorkManager, at least 15 minutes apart) reads the last 3 days with the background-read permission. Best effort: Doze and app standby delay it. |
| Per friend | Every leaderboard row shows "updated X ago" from that member's `lastSyncedAt`, and dims members who have not synced for 90 minutes. |
| Settling | A day settles at 10:00 the next morning in the uploader's timezone. After that an existing value for that day is frozen, so late edits cannot change results. A day with no value yet can still be filled in by a first-time backfill. |

## Leaderboards and challenges

Ranges are computed in the group's timezone. Today is today; week is Monday to today (ISO week);
month is the 1st to today; three months is the last 90 days. Ranking is competition style: ties
share a rank and the next rank is skipped (1, 1, 3).

Challenges belong to a group. A weekly challenge runs 7 days from its start date; a monthly one
runs until the day before the same date next month. By default all current members take part,
and members can join or leave while it is upcoming or live. Status goes UPCOMING, ACTIVE,
SETTLING (after the last day until 10:00 the next morning) and FINISHED. A finalizer runs every
minute: when a challenge finishes it records the winners (several on a tie) and a snapshot of the
final standings, which the API serves from then on.

## Realtime

Clients connect to the Socket.IO namespace `/realtime` with their access token. The server puts
each socket in a `group:<id>` room for every group the user belongs to. `steps.updated` is sent
when a member uploads and `group.updated` when members, challenges or results change. The app
treats events as hints and refetches. The socket is only open while the app is in the foreground.

## Demo mode

With `DEMO_MODE=true` the API seeds a "Steppy Demo" group with five synthetic friends and a demo
captain account (`demo@steppy.app` / `steppy-demo`), 90 days of history, a live weekly and monthly
challenge and a finished one. A ticker adds plausible steps to the synthetic users every minute
so leaderboards move while you watch. `POST /auth/demo` (the app's "Try the demo" button) creates
a guest who joins that group. The guest's own steps come from the phone: either a real health
store or the on-device `DEMO` source, which generates deterministic realistic numbers. On the iOS
Simulator, development builds can also write 90 days of sample steps into HealthKit so the real
HealthKit read path can be tried.

## Security notes

- Passwords are hashed with bcrypt. Access tokens are short-lived JWTs (15 minutes). Refresh tokens are
  opaque, stored hashed and rotated on every use.
- Every group, leaderboard, history and challenge route checks membership and returns 404 to
  non-members. Adding someone to a group requires being their friend.
- In production the API refuses to start without a strong `JWT_ACCESS_SECRET` and a `CORS_ORIGIN`
  list. `/auth` routes are rate limited per client IP (set `TRUST_PROXY` behind a reverse proxy).
- Health write permissions exist only in development builds (`STEPPY_PRODUCTION=1` removes them).
